skywalkingreceiver-cola · v0.159.0

用 ClickHouse 承接 SkyWalking Profile：一套能画火焰图、也能下钻链路的方案

Agent 的剖析不是 pprof，而是「领任务 → 命中 endpoint 后按间隔 dump → 结束回写状态」。 只留两张表：任务用 INSERT + FINAL 看最新状态；快照按 segment_id + sequence 存时间线。火焰图对快照现算，链路用 segment_id 对齐 span。

最优方案一句话

任务表一行一个实例，status=running/finished。 Receiver SELECT ... FINAL 后再按主键去重下发； Finish 再 INSERT 一行，该实例不再领同一任务。 快照一行一次 dump；点 span 用 segment_id，火焰图对 snapshots 现算。

1. 为什么这是最优

对比过 YAML 静态任务、转 logs、转 pprofile、走官方 otel_profiles 表、以及边表 + finish 表。当前落地是「两张 CK 表 + INSERT 覆盖状态 + 查询时现算火焰图」。

方案 任务来源 火焰图 按 Trace 下钻 结论
YAML profile_tasks + logs 配置文件，改任务要发版 栈在 log body 里，聚合费劲 属性能带 segment，但不一等公民 适合 Demo，不适合你们只认 CK 的生产
OTel pprofile + 官方 profiles 表 仍要另找任务源 模型是 CPU sample，和 SW 线程 dump 别扭 缺 sequence / segment 语义 信号时髦，查询对不齐业务
CK 任务表 + 快照明细（无边表） SQL INSERT 任务；Finish 再 INSERT 状态 Array 栈，查询时 ARRAY JOIN 现算 segment_id 对齐 span；otel_trace_id 可空 选定。两张表覆盖控制面和数据面
控制面

任务只存在 CK

Agent 轮询很勤，RPC 不打库。每 15s SELECT ... FINAL，按主键 updated_at 去重后进内存。下发看 service / 实例 / status / lastCommandTime，不按 StartTime、Duration 过滤。

数据面

快照直写专用表

一行一次 dump。同一 segment_id 会有多行（sequence 0、1、2…，间隔 = dump_period_ms）。能补则补 TraceId，空了用 segment_id 查。

查询面

一张明细，两种查法

点开 span 用 segment_id 读栈序列；任务/时间范围火焰图对同一张表 ARRAY JOIN 现算。

2. 全链路架构

Profile 控制与存储由 cola receiver 直连 ClickHouse；Traces 仍走现有 clickhouseexporter，两套数据用 TraceId / segment_id 会合。

3. 三个 RPC 各自干什么

这是 SkyWalking in-process profiling，不是 eBPF，也不是 pprof。没有第一条 Command，后面两条永远不会来。

GetProfileTaskCommands

Query：service / serviceInstance / lastCommandTime。内存匹配，不打 CK。同一 task_id 只下发一条；实例行优先于广播行 ''。

CollectSnapshot

流式 dump。同一请求（同一 traceSegmentId）会有多条，sequence 递增。协议没有 traceId，能补则补。

ReportTaskFinish

实例级结束通知。再 INSERT 一行 status=finished（主键含该实例），回空 Commands。该实例不再领同一任务。

3.1 下发规则与任务状态

查结束看 status，不要看窗口是否过期。窗口只给 Agent 用；Receiver 下发不按 StartTime / Duration 过滤。

写入

INSERT 即最新状态

主键 (service, task_id, service_instance)。建任务 status='running'。某实例 ReportTaskFinish 再 INSERT 一行同主键、status='finished'，内存立刻 Upsert，不用等 15s。

A 结束只动 A 那一行。广播行 service_instance='' 仍会发给未结束的实例。

下发

何时不下发

加载：SELECT ... FINAL 后按主键用 updated_at 去重（merge 前 FINAL 仍可能重复）。

跳过：finished / enabled=0 / 服务名不对 / 实例不匹配 / create_time ≤ lastCommandTime / 该实例已有同 task_id 的 finished 行。

4.1 每张表的字段

来源：人工/SQL 写入任务；Agent 协议；Receiver 补齐；任务表带入；ClickHouse 物化/默认。

sw_profile_tasks · 剖析任务（人工 INSERT）

ORDER BY (service, task_id, service_instance)，ReplacingMergeTree（无版本列）。Java Agent 在收下 Command 后会按 ProfileConstants 校验，非法值会丢掉任务但仍更新 lastCommandTime。

字段类型来源说明
task_idStringSQL 任务唯一 ID，下发给 Agent 的 TaskId。更新同一任务用相同 id 再 INSERT 一行（Replacing 按 updated_at 留最新）。
serviceStringSQL SkyWalking 服务名，必须等于 Agent 的 SW_AGENT_NAME（例如 sk.colasoft.cas.alarm）。不是 OAP 的 base64 service_id。
service_instanceStringSQL 进主键。空字符串 = 该服务下所有实例都下发。非空则必须等于 SW_AGENT_INSTANCE_NAME。一行一个实例，A 停用不会覆盖 B。
endpoint_nameStringSQL 与入口 span 的 operationName 完全一致，如 POST:/cmc_alarm/alarm/message。Agent 只对首个 span 名相等的请求采栈。
duration_secondsUInt32SQL 任务持续秒数。下发 Command 时换成分钟（向上取整）。Agent 要求 1–15 分钟。
min_duration_threshold_msUInt32SQL 入口 span 耗时低于该毫秒数则不采。0 = 命中 endpoint 就采。
dump_period_msUInt32SQL 线程栈采样间隔（毫秒）。Agent 要求 ≥ 10。估算帧耗时：sample_count × dump_period_ms。
max_sampling_countUInt32SQL 本任务最多采几条请求。Agent 要求 1–9（必须 < 10）。官方 UI / PG 常见值为 5。填 10 或 20 会被 Agent 丢弃。
start_timeDateTime64(3)SQL Agent 侧开始时刻，下发为 epoch 毫秒。可晚于现在，Agent 会等到点再采。
create_timeDateTime64(3)SQL 任务创建时间，下发为 epoch 毫秒。Agent 用 lastCommandTime 去重：只有 create_time > lastCommandTime 才收下。改任务必须刷新本字段。
serial_numberStringSQL Command 的 SerialNumber，可与 task_id 相同。
enabledUInt8SQL 1 可下发，0 人工停用。与 status 独立：停用整行，不影响其他实例。
statusStringSQL / Finish running（默认）或 finished。ReportTaskFinish 再 INSERT 一行，主键含该实例，FINAL 后即为结束。该实例不再领同一 task_id。
extraStringSQL 预留备注 / JSON，Receiver 不读。
updated_atDateTime64(3)默认 now64 普通列。Receiver 加载任务：SELECT ... FINAL 后再按主键用 updated_at 去重，避免 merge 前重复行被下发两次。

sw_profile_snapshots · 线程 dump 明细

协议 ThreadSnapshot 只有 taskId / traceSegmentId / time / sequence / 栈。没有 per-frame 耗时，也没有 traceId。

字段类型来源说明
timestampDateTime64(3)Agent 本次 dump 时刻（ThreadSnapshot.time 毫秒）。分区键 toDate(timestamp)，TTL 14 天。
task_idStringAgent 对应任务。Agent 原样回传 Command 里的 TaskId。
serviceString任务 / LRU 优先按 task_id 从任务缓存带入；没有则用 segment LRU 里的服务名。两者都 miss 才为空。
service_instanceString任务 / LRU 任务指定了实例则用任务值；否则尝试用 segment LRU 里的实例名。
endpoint_nameString任务表 任务上的 endpoint，不是 Agent 再报一次。
otel_trace_idStringLRU 同进程先收到该 segment 的 traces 时填入（OTel 16 字节 hex）。快照早于 segment、或 traces 只走 Kafka 时为空。查询请用 segment_id 关联。
sw_trace_idStringLRU SkyWalking segment.traceId（如 xxx.180.yyy）。同样依赖 LRU，可空。
segment_idStringAgent 与链路关联的主键。ThreadSnapshot.traceSegmentId。官方 OAP 也用它 JOIN segment。对齐 otel_traces.SpanAttributes['sw8.segment_id']。
sequenceUInt32Agent 同一请求内第几次 dump，从 0 递增。一行不是一条请求；行数 ≈ 请求耗时 / dump_period_ms。连续两行栈可以完全相同（还停在同一方法）。
stack_leaf_firstArray(String)Agent Agent 原数组：[0] 是栈顶（leaf / 当前方法），末元素靠近线程入口。
stack_root_firstArray(String)MATERIALIZED arrayReverse(stack_leaf_first)，根在下，供查询时画火焰图。不要在应用层再反一次。
stack_hashUInt64MATERIALIZED 对 stack_root_first 做 xxHash64，便于按整栈去重或聚合。
stack_depthUInt16MATERIALIZED 栈帧个数，length(stack_root_first)。
不再建 sw_profile_flame_edges / sw_profile_task_finish。单次 segment 或某个任务的火焰图，对 sw_profile_snapshots 做 ARRAY JOIN 现算。

快照表 DDL（核心）

CREATE TABLE otel.sw_profile_snapshots
(
    timestamp        DateTime64(3) CODEC(Delta, ZSTD(1)),
    task_id          LowCardinality(String),
    service          LowCardinality(String),
    service_instance String,
    endpoint_name    LowCardinality(String),
    otel_trace_id    String CODEC(ZSTD(1)),
    sw_trace_id      String CODEC(ZSTD(1)),
    segment_id       String CODEC(ZSTD(1)),
    sequence         UInt32,
    stack_leaf_first Array(String) CODEC(ZSTD(1)),
    stack_root_first Array(String) MATERIALIZED arrayReverse(stack_leaf_first),
    stack_hash       UInt64 MATERIALIZED xxHash64(arrayStringConcat(stack_root_first, '\n')),
    stack_depth      UInt16 MATERIALIZED length(stack_root_first),
    INDEX idx_otel_trace otel_trace_id TYPE bloom_filter(0.001) GRANULARITY 1,
    INDEX idx_sw_trace   sw_trace_id   TYPE bloom_filter(0.001) GRANULARITY 1,
    INDEX idx_task       task_id       TYPE bloom_filter(0.01)  GRANULARITY 1,
    INDEX idx_ts         timestamp     TYPE minmax GRANULARITY 1
)
ENGINE = MergeTree
PARTITION BY toDate(timestamp)
ORDER BY (segment_id, sequence)
TTL toDate(timestamp) + INTERVAL 14 DAY
SETTINGS ttl_only_drop_parts = 1;
栈方向：Java codeSignatures[0] 是栈顶（leaf）。火焰图要根在下，所以表内物化 stack_root_first = arrayReverse(...)。写入只存 Agent 原数组，避免应用层搞反。

任务表 DDL

CREATE TABLE otel.sw_profile_tasks (
  task_id String,
  service String,
  service_instance String DEFAULT '',
  endpoint_name String,
  duration_seconds UInt32,
  min_duration_threshold_ms UInt32,
  dump_period_ms UInt32,
  max_sampling_count UInt32,
  start_time DateTime64(3),
  create_time DateTime64(3),
  serial_number String,
  enabled UInt8 DEFAULT 1,
  status LowCardinality(String) DEFAULT 'running',
  extra String DEFAULT '',
  updated_at DateTime64(3) DEFAULT now64(3)
)
ENGINE = ReplacingMergeTree
ORDER BY (service, task_id, service_instance);

5. 和 Trace 怎么关联

协议不带 TraceId。写入时能补则补；查询主路径是 segment_id，不要依赖 otel_trace_id 非空。

写入路径（主路径）

同一 swReceiver 先收 traces。每次 ConsumeTraces 把

sw8.segment_id → {otel_trace_id, sw_trace_id, service}

放进 LRU（约 10 万条 / 10 分钟）。快照到达时填两列 TraceId。快照早到、或 traces 只走 Kafka 时为空，属正常。

查询路径（会合）

Span 树：otel_traces WHERE TraceId = ?，树边是 SpanId / ParentSpanId。

栈序列：snapshots WHERE segment_id = ? ORDER BY sequence。

对齐慢 span：snapshots.segment_id = SpanAttributes['sw8.segment_id']。

6. 两种查询，两张表

任务 / 时间范围火焰图

对 snapshots 现算，给 d3-flamegraph / Grafana 树。

SELECT
    if(d = 1, '', stack_root_first[d - 1]) AS parent_frame,
    stack_root_first[d] AS frame,
    count() AS value
FROM otel.sw_profile_snapshots
ARRAY JOIN arrayEnumerate(stack_root_first) AS d
WHERE task_id = {task_id:String}
  AND timestamp BETWEEN {from:DateTime} AND {to:DateTime}
GROUP BY parent_frame, frame
ORDER BY value DESC;

单次 Trace 的层级 + 栈

一次 HTTP ≈ 一个 segment ≈ 多行 dump。不要按 segment_id 去重只留一行。

-- span 树
SELECT SpanId, ParentSpanId, SpanName, Duration,
       SpanAttributes['sw8.segment_id'] AS segment_id
FROM otel.otel_traces
WHERE TraceId = {id:String};

-- 该 segment 的 dump 时间线（多行）
SELECT timestamp, sequence, stack_root_first
FROM otel.sw_profile_snapshots
WHERE segment_id = {segment_id:String}
ORDER BY sequence;

-- 这次请求的火焰图
SELECT
    if(d = 1, '', stack_root_first[d - 1]) AS parent_frame,
    stack_root_first[d] AS frame,
    count() AS value
FROM otel.sw_profile_snapshots
ARRAY JOIN arrayEnumerate(stack_root_first) AS d
WHERE segment_id = {segment_id:String}
GROUP BY parent_frame, frame;

7. 可用性怎么保证

存储

集群用 ReplicatedMergeTree + Keeper。分区按天，TTL 只丢 part。快照按 (segment_id, sequence) 排序，时间范围靠 minmax 跳数索引。

读取任务

多副本 Receiver 各自缓存。CK 短暂失败时保留上一份缓存并打 error，禁止把失败当成「无任务」——否则 Agent 会停采。

写入快照

5000 行或 1s 攒批同步 INSERT。小流量可开 async_insert。不走外部 batch processor，避免 profile 和 traces 抢同一队列语义。

8. Receiver 配置与职责边界

receivers:
  skywalking_cola:
    protocols:
      grpc:
        endpoint: 0.0.0.0:21800
    clickhouse:
      dsn: tcp://ch-host:9000
      database: otel
      tasks_table: sw_profile_tasks
      snapshots_table: sw_profile_snapshots
      task_refresh_interval: 15s
      insert_batch_size: 5000
      insert_flush_interval: 1s

service:
  pipelines:
    traces:
      receivers: [skywalking_cola]
      exporters: [clickhouse]   # 现有 traces 表
    # profile 不进 pipeline，receiver 直写 CK
Profile 不进入 Collector logs/profiles pipeline。原因：任务要读 CK、快照要精确列类型、还要和同进程 traces 共享 LRU。硬塞 exporter 会丢掉这些约束。Traces / Metrics 保持原 pipeline。

第一版明确不做

YAML 当任务主存储 写入 otel_logs / otel_profiles 查询时再 JOIN 补 TraceId 当主路径 eBPF / Continuous Profiling HTTP 收 snapshot Collector 内建任务 UI
